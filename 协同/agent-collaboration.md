# PortPilot 多 Agent 协同框架

> 本文件定义 PortPilot 项目**多个共创智能体（agent）如何协同工作**的机制：agent 身份如何确认、进度如何被监控、任务如何分工与认领、冲突如何避免。它是《项目共创准则.md（AGENTS.md）》的协同执行细则，与准则配套使用。
>
> 适用对象：进度监控 agent（PM）、代码编写 agent（Dev）、代码评审 agent（Reviewer）、以及任何在本项目并发工作的 agent。

---

## 一、设计原则

1. **看板即唯一事实源（Kanban as Single Source of Truth）**：所有任务的**存在、认领、状态、归属、验收**都以 GitHub Projects 看板为准。任何 agent 不得凭记忆或本地推测判断"有哪些活、谁在做、做到哪步"，一律以看板实际数据为准。
2. **显式角色（Explicit Roles）**：每个 agent 会话启动即声明角色，角色决定它能做什么、不能做什么（权限边界）。
3. **分配加锁（PM 单点分配）**：任务互斥不靠 assignee（共享 token 下 assignee 无法区分并发 agent，见 3.3 竞态结论），而是收敛到**单点 PM 分配**——任务一旦经 PM 分配给某 Dev（评论登记 `@<会话名>`），对其他 agent 即"加锁"，避免多头并行抢占同一任务。
4. **状态机合法流转（Legitimate State Flow）**：看板状态列只能按定义的方向流转，禁止跳列，保证进度可追溯、可审计。
5. **证据可回溯（Traceable Evidence）**：每个任务的状态推进必须附可观测证据（PR、CI run、测试报告），无证据不推进。

---

## 二、协同模型总览

```
┌──────────────────────────────────────────────────────┐
│            GitHub Projects 看板（唯一事实源）           │
│   待研发 → 研发中 → 待验收 → 已验收 → 已关闭            │
│   （assignee / milestone / 状态字段 在此维护）           │
└──────────────────────────────────────────────────────┘
         ▲ 分配/更新/汇报        ▲ 审核PR/签发结论     ▲ 扫描/调度/校验
         │                       │                     │
┌────────┴─────────┐   ┌─────────┴─────────┐ ┌─────────┴─────────┐
│  代码编写 agent   │◄─►│   代码评审 agent   │◄►│   进度监控 agent   │
│  (Dev, 可多个)    │  审核 │  (Reviewer, ≥1)  │  │  (PM, 仅一个)      │
└──────────────────┘   └───────────────────┘  └───────────────────┘
```

- **Dev（代码编写）**：只做「实现 PM 分配的任务 → 测试 → 提交 PR → 移列」，与"做什么"无关的看板治理动作（建任务、拆任务、调里程碑、自行分配）一律不做。
- **Reviewer（代码评审）**：只做「PR 进入评审后独立审核」，用可观测手段核验 PR 是否符合项目约束、是否完善了功能，签发 PASS/FAIL 结论；不写功能代码、不移动看板列。
- **PM（进度监控）**：只做「扫描 → 调度 → 校验 → 报告」，不直接写功能代码，专注于让整个流水线有序前进。

## 三、Agent 角色与身份确认

### 3.1 角色定义

| 角色 | 代号 | 数量 | 核心职责 | 允许的动作 | 禁止的动作 |
|------|------|------|---------|-----------|-----------|
| 进度监控 agent | PM | 1 | 盯全局进度、**单点分配任务**、校验状态流转、产出进度报告 | 扫描看板、创建/拆分任务、设置里程碑、**分配任务给 Dev**、校验并纠正状态列、汇总报告 | 认领并实现功能代码 |
| 代码编写 agent | Dev | ≥1 | 实现 PM 分配的功能、跑测试、提交 PR | 实现 PM 分配的任务、编译测试、提交 PR、将本人任务移列（移列前确认验收归属） | 创建/拆分任务、调整里程碑、治理其它任务、自行抢占任务 |
| 代码评审 agent | Reviewer | ≥1 | **独立审核 PR 是否符合项目约束、是否完善了功能**，签发 PASS/FAIL 结论 | 拉取 PR 代码、读契约/架构文档、编译测试、按评审维度核验、在 PR/Issue 评论签发结论 | 认领并实现功能代码、移动看板列、修改他人代码、批准合入 |

### 3.2 身份确认机制

每个 agent 会话启动时，**必须**按以下顺序确认身份与权限边界，确认完成前不得执行任何看板写操作：

1. **读 AGENTS.md**：进入任何会话，先读仓库根《项目共创准则.md》与本文档，明确自身角色。
2. **角色注入**：角色由外部启动参数强注入，`AGENT_ROLE=pm|dev|reviewer`。**未注入角色时一律视为只读巡检**（只能扫描看板、读文档，禁止任何认领/写状态等动作），避免 agent 自行扩展权限。agent 会话启动时必须自检：若 `AGENT_ROLE` 未设置或无法确认，则降级为只读，不得执行写操作。
3. **任务归属校验（PM 分配制）**：Dev 只实现 PM 通过任务 Issue 评论 `@<会话名>` 分配给自己、且未被其它 `@<会话名>` 认领的任务；发现任务已分配给他人仍动手 = 越权，应被拒绝并报告 PM。
4. **能力边界不可越**：PM 不做功能实现，Dev 不做任务治理，Reviewer 不做实现/移列/合入。越界动作应被 PM 或评审 subagent 拦截。
5. **角色自检断言**：每次执行写操作（分配/移列/改里程碑/签结论）前，agent 必须断言自身角色与目标权限匹配；断言失败即中止并报告，不静默继续。

### 3.3 身份标识与任务归属（并发控制核心）

> **并发竞态结论（已实测核验）**：GitHub 的 Issue `assignees` 是数组，但 `--add-assignee` 对同一用户**去重**。当多个 Dev **复用同一 token** 时，所有 `@me` 都解析为同一账号，assignee 恒为单元素，**无法用 assignee 区分并发 agent**；且 GitHub 无原子 CAS 写，任何"Dev 自取 assignee + 回读校验"都带竞态窗口。因此：**assignee 不能作为排他锁**。

- **分配权收敛到单点 PM**：任务归属的唯一事实源 = **PM 分配清单 + 任务 Issue 评论中的 `@<会话名>` 认领记录**，而非 assignee 字段。只有 PM（或项目维护者）执行"分配任务给某 Dev"，Dev **不得自行添加 assignee 抢占**。
- **Dev 认领前置防御检查**：Dev 只认领 PM 已通过 Issue 评论/分配清单下发给自己的任务。动手前必须防御检查，任一不满足即跳过并报告 PM，不产生任何写操作：
  ```bash
  # 检查该任务是否已被分配给他人（= 评论中已有其它 @会话名 认领记录 或 状态列=研发中）
  # 用 gh 查询该 Issue 的评论与状态，若已被他人认领则 exit 1（不写，避免并发写）
  ```
- **认领落地（仅 PM 执行分配）**：
  ```bash
  # PM 分配：设 assignee（指向目标 Dev 账号）+ 状态列→「研发中」+ 评论登记 @<会话名>
  gh issue edit $NUM --add-assignee <dev-account> -R OneForAll20240313/PortPilot
  gh project item-edit --id "$ITEM_ID" --project-id "$P" --field-id "$FID" --single-select-option-id "$OPT_ID"
  gh issue comment $NUM -R OneForAll20240313/PortPilot -b "@<会话名> 已认领（PM 分配）"
  ```
- **共享 token 下的归属判定**：各 Dev 以 `AGENT_ROLE=dev:<会话名>` 声明唯一标识；PM 通过任务评论里的 `@<会话名>` 记录区分"谁在干哪个任务"，据此统计各 Dev 进度；assignee 仅作展示，不作归属依据。

### 3.4 看板项三关联（Issue ↔ PR ↔ 归属 Dev）

> **原则**：看板上的每个任务项必须是"可追溯、可归属"的完整闭环。任何 agent 查看看板时，应能从任务项直接跳到：① 它对应的 PR；② 它被分配给了哪个 Dev；③ 该 Dev 是哪个会话。三者缺一，视为"看板项不完整"，PM 扫描时应纠正。

1. **Issue ↔ PR 关联（已完成）**：PR 标题/描述必须用 `Closes #<issue号>`（合入自动关闭）或 `Related #<issue号>`（仅关联）标注对应任务 Issue，保证「任务 Issue ↔ PR ↔ CI run ↔ 测试报告」四者互联。
2. **Assignees 关联（归属看板化）**：PM 分配任务时，除评论登记外，**必须 `--add-assignee` 指向目标 Dev 账号**，并尽量利用看板 `Assignees` 字段，使看板卡片上直接可见归属。**注意（已实测核验）**：共享 token 下 assignee 恒为单元素、无法区分并发 agent，故 assignee **仅作展示/筛选**，**不作并发锁与归属事实源**；真正的归属唯一事实源仍是评论 `@<会话名>` 记录。
3. **归属 Dev 详细身份（评论登记）**：PM 分配时在 Issue 评论**详细登记**目标 Dev 的完整身份，格式为：
   ```
   @<会话名>（AGENT_ROLE=dev:<会话名>）已认领，本任务归属 dev:<会话名>
   ```
   会话名必须唯一、可区分；Dev 在交付/移列/汇报时，同样以 `dev:<会话名>` 自报身份，确保"谁干的活"在看板、PR、评审、验收各环节可对得上。
4. **Reviewer 关联（审核归属）**：评审 agent 以 `AGENT_ROLE=reviewer:<会话名>` 在 PR 评论署名，结论落盘到 PR 与关联 Issue，形成"实现者(dev) + 审核者(reviewer)"完整责任链。

## 四、任务分工与认领（并发控制核心）

### 4.1 Dev 工作循环（认领 → 实现 → 交付）

```
loop:
  1. 扫描看板当前里程碑（M1）的【待研发】列，收集 PM 待分配任务
  2. 只看被 PM 分配给自己（Issue 评论含 @自己的会话名）的任务；未分配不自行认领
  3. 认领前置防御检查：确认该任务未被分配给他人（评论无其它 @会话名 认领、状态列=待研发）→ 通过才继续，否则跳过并报告 PM
  4. 领取即标记【研发中】（原子同刻），Issue 评论登记 `@<会话名>（AGENT_ROLE=dev:<会话名>）已认领`
  5. git pull --rebase 拉取最新代码
  6. **开工前通读上下文（强制，防再犯架构约束违规）**：认领后、动工前，必须把"本任务 + 本任务对应的文档相关内容"重新通读一遍，确认与当前架构/契约一致后再实现。具体见下方「开工前上下文通读」。
  7. 实现功能（严格按契约 service-api.md / schema）
  8. 按六段式进度打点在 Issue 评论即时更新进度（见下方「Dev 六段式进度打点」）
  9. 建 `feat/<模块>`/`fix/<模块>` 分支 → commit → push → 开 PR → 等待 CI 通过
     （merge 走 squash；`trae/<session>` 等自动化分支一律不得合入 main，见准则「仓库治理·防污染红线」）
     **PR 必须关联任务 Issue**：PR 标题/描述用 `Closes #<issue号>`（合入自动关闭）或 `Related #<issue号>`（仅关联）标注对应任务，保证「任务 Issue ↔ PR ↔ CI run ↔ 测试报告」四者互联，验收证据链可互跳。
  10. 【等评审】PR 进入评审通道，由**评审 agent（Reviewer）**独立审核（见 4.3 评审关卡）：核验 PR 符合项目约束、功能完善，签发【PASS】/【FAIL】结论
  11. 评审【FAIL】→ 任务状态→【待修正】，Dev（或后续认领修正任务的 Dev）按评审意见修复 → pull --rebase → 重新 push/CI → 重新请求评审
  12. 评审【PASS】→ 将任务状态→【待验收】，在 Issue 评论附：结论 + 测试报告链接 + CI run 链接 + 评审结论
  13. 【立即停下】完成当前任务后不做任何新认领：不自行领取下一个任务、不继续开工，等待 PM 对本任务验收（状态→已验收）
  14. 【逐个验收】本任务被 PM 验收通过（已验收/已关闭）后，才回到 1 重新扫描，等 PM 分配下一个任务
```

#### 开工前上下文通读（认领后必读，防再犯架构约束违规）

> **目的**：此前出现过"实现偏离架构"的问题（如 Core 层出现冗余的 `core::device_port.h` 第二套接口、未按"DevicePort 归 Domain 层"实现）。为杜绝同类违规，Dev 认领任务后、动工前**必须先通读本任务及其对应文档上下文**，确认实现方向与当前架构/契约一致，再开始写代码。

- **通读清单（按任务涉及层次针对性选读，不遗漏）**：
  1. **任务本身**：任务 Issue 正文 + 关联 PR/评论 + 三关联项（Issue↔PR↔归属 Dev，见 3.4）；
  2. **本任务所属模块的架构章节**：`产品/portpilot-design/13-architecture-design.html`（分层定义、组件归属、接口编号 A-xxx/P-xxx）、`14-module-design.html`；
  3. **本任务涉及的契约 SSOT**：`contracts/service-api.md` 对应接口、`events.md`、相关 schema；
  4. **跨平台/分层约束**：确认本任务落在哪一层（core/domain/service/ui），是否触犯"Core 禁止直接依赖 Qt"、依赖单向、DevicePort 归 Domain 等架构红线（见 7.1 技术栈契约）；
  5. **相关既有代码**：本模块现有实现，确认在既有结构上扩展而非另起炉灶。
- **通读产出**：动工前在 Issue 评论打进度点 `已完成上下文通读，确认本任务归属 <层>、<模块>，按 <文档章节/契约> 实现`，并自检一句"本任务是否触犯任何架构红线"；若发现任务描述与架构/契约冲突，**停下报告 PM**，不擅自定夺。
- **若任务为「待修正」（评审 FAIL 后补领）**：额外通读原 PR 的评审结论（【FAIL】缺陷清单）与关联架构红线，先审查原产物再修复（见 4.5）。

#### Dev 六段式进度打点（每个阶段完成即时在 Issue 评论更新）

> **目的**：让 Dev 的研发过程从"黑盒"变为"可观测"——PM、定时器、用户都能通过评论留痕判断任务究竟走到哪一步、是否仍在进行中（配合「残局补领判定」，见 4.5）。每个打点都是一条 Issue 评论，刷新任务「最后活跃时间」。

| 阶段 | 触发时机 | Issue 评论内容（打点） | 看板状态 |
|------|---------|----------------------|---------|
| ① 认领 | PM 分配后 | `@<会话名> 已认领，开始研发` | 研发中 |
| ② 源码完成 | 代码实现写完后 | `源码完成，开始本地编译验证` | 研发中 |
| ③ 编译通过 | 本地 `cmake --build` 成功 | `本地编译通过` | 研发中 |
| ④ 单测通过 | `ctest` / 单元测试全绿 | `单元测试通过` | 研发中 |
| ⑤ 提交 PR | PR 创建并 push 后 | `PR #<num> 已提交，Closes #<issue>，待 CI` | 研发中 |
| ⑥ CI 通过 | CI 运行成功 | `CI 通过，请求评审 @评审agent` | 研发中 |

> 打点是**过程留痕**，不改变「一次性一件、逐个验收」：一个会话从认领一路打到评审 PASS 移「待验收」后停止。打点让"卡在哪一步"可定位（如「编译通过」后 2 小时无下一步评论 → 判定卡在提交 PR 环节）。

> **一次性一件、逐个验收**（用户强制规则）：每个 Dev **同时只认领一个任务**，该任务完成并移入「待验收」后**立即停下**，不连续认领/领取下一个任务。必须等当前任务被 PM 验收通过（状态→已验收）后，才允许认领下一个。**不允许"认领即停、唯有完成就继续领取"的连轴转模式**——每个任务都要被独立验收，达到"一个一个验收完再继续"。若 PM 已分配下一个而当前任务未验收，Dev 应停下并提示 PM 先验收。

### 4.2 分配即加锁（PM 单点）

- **分配权唯一在 PM**：任务「待研发→研发中」的流转由 **PM 单点执行**（设 assignee + 移列 + 评论登记 `@<会话名>`）。因为多 Dev 共享 token 时 assignee 无法区分彼此，**Dev 不得自行 add-assignee 抢占**（见 3.3 竞态结论）。
- **加锁语义**：一旦 PM 将任务分配给某 Dev（评论写入 `@<会话名>` 认领记录），该任务对其它 Dev 即"上锁"——其它 Dev 的防御检查会因"评论已有其它 @会话名 认领"而跳过。
- **领取即标记研发中（强制）**：任务**被领取（认领）的那一刻，看板状态必须同步标记为「研发中」**。不允许出现"已领取/已开工但状态仍为待研发"的悬挂状态。领取动作（PM 分配）与「待研发→研发中」移列必须**原子、同刻完成**；Dev 一旦拿到 PM 分配开始动手，即视为该任务已进入「研发中」，若看板仍显示「待研发」，Dev 应提示 PM 立即修正状态列。
- **半分配处理**：若出现"已移研发中但无认领评论"或反之，视为非法，PM 扫描时自动纠正回「待研发」并清空残留登记。

### 4.3 评审关卡（Reviewer Gate）

> **评审 agent（Reviewer）是 PR 合入前的独立质量关卡**：Dev 提交 PR 后，必须经 Reviewer 独立审核并签发 PASS，任务才可进入「待验收」；FAIL 则打回 Dev 修复。评审执行者与实现者分离，避免"自写自审"。

- **谁触发**：Dev 开 PR 且 CI 通过后，在 PR/Issue 评论请求评审（`@评审agent`）；Reviewer 执行器自驱 cron 周期性扫描"研发中+已关联 PR+CI 通过"的任务时介入评审。
- **Reviewer 审核什么**（涵盖准则第二章第 6 条 7 维，并叠加项目约束维度，逐项核验）：
  1. **符合项目约束**：PR 是否关联任务 Issue（`Closes/Related #issue`）；是否遵循契约（service-api.md / schema）；是否遵循分层与架构约束；是否违反仓库治理（分支规范、防污染红线、最小改动）；
  2. **功能是否完善**（准则第 6 条 7 维）：①按需求与契约正确实现 ②无明显 Bug ③内存管理合理 ④编译通过 ⑤无明显性能问题 ⑥接口符合定义、模块功能完善 ⑦不破坏框架结构。
- **评审动作**：拉取 PR 分支代码 → 读契约/架构/需求文档 → 编译 + 跑测试 → 逐维核验 → 在 PR 评论签发结论（结构标记 + 逐条证据 + 严重度分级缺陷清单）。
- **评审结论结构化标记（让任何 agent/定时器一眼识别）**：Reviewer 在 PR 与关联 Issue 评论签发统一格式结论，首行必须是结构化标记：
  ```
  @评审agent 评审结论：【PASS】/【FAIL】
  - 阻塞项：S1 xxx（严重）
  - 待修项：G1 xxx（一般）、G2 xxx（一般）
  - 建议项：xxx（改进）
  ```
  - **【PASS】** = 7 维 + 项目约束全部通过 → 明确"建议进入待验收"；
  - **【FAIL】** = 存在「严重」缺陷或「一般」缺陷多条未决 → 明确"阻止合入、待修正"。
  同时将结论同步到关联任务 Issue 评论，并**建议在 Issue 标题加 `[待修正]` 前缀**（若为 FAIL），使扫描 agent 能按评论前缀 + 状态列快速识别。
- **结论约束**：Reviewer 只签**审核结论**，不直接合入、不移动看板列、不修改代码；PASS 结论由 PM 确认后作为「待验收」前置证据。
- **FAIL 处理**：Reviewer 签发【FAIL】后，任务状态由 PM（或 Dev 提示 PM）移至【待修正】列；Dev（或后续认领修正任务的 Dev）按缺陷清单修复 → 重新 push → 重新走 CI → 重新请求评审。修复完成、复审【PASS】后，任务才移「待验收」。

### 4.4 状态机合法流转

| 当前状态 | 允许流转到 | 触发条件 |
|---------|-----------|---------|
| 待研发 | 研发中 | PM 单点分配（设 assignee + 移列 + 评论登记 `@<会话名>`） |
| 研发中 | 待验收 | PR 合并 + CI 通过 + 测试报告已附 + **Reviewer 评审 PASS** |
| 研发中 | 待修正 | Reviewer 评审 **FAIL**（有权重缺陷，PM 移至待修正列） |
| 研发中 | 待研发 | 分配后放弃/回退（PM 释放） |
| 待修正 | 研发中 | Dev 认领修正任务，开始修复（领取即标记研发中） |
| 待修正 | 待验收 | 修复完成 + 复审 **PASS** |
| 待验收 | 已验收 | PM 执行验收五要素校验通过（证据链完整） |
| 已验收 | 已关闭 | 无遗留问题，正式关闭 |
| 已关闭 | — | 终态，不再流转 |

> **状态链**：待研发 → 研发中 →（待修正 ⇄ 研发中）→ 待验收 → 已验收 → 已关闭。
> 禁止跳列（如 待研发→已验收、研发中→已关闭、待修正→已验收）。非法流转由 PM 扫描自动纠正。
>
> **残余框说明**：「待修正」是评审 FAIL 后的中间态，用于标识"评审已过但需修正"——任何 agent 认领时看到【FAIL】标记 + 待修正列，即知该任务需修正后再复审，而非全新任务。
>
> **验收归属**：「待验收 → 已验收」由 **PM**（或由 PM 指定的独立验收者）执行验收五要素校验后移动；Dev 无权自行将本人任务移入「已验收」。验收五要素见准则第二章第 5 条（符合产品定义 / 功能可用好用 / 证据链完整 / 标准清晰可测 / 留档可追溯）。

### 4.5 冲突处理

- **代码冲突**：`git pull --rebase` 变基解决；冲突无法自动合并时，报告 PM 协调，禁止强推覆盖。
- **看板冲突（PM 单点下不应发生）**：因任务「待研发→研发中」仅由 PM 单点分配，正常情况下不会出现两个 agent 抢占同一任务；若出现异常（如重复分配），以 **PM 分配清单 / 任务 Issue 评论 `@<会话名>` 认领记录**为唯一事实源，后分配者退出。
- **同一文件并行修改竞态**：两个 Dev 同时修改同一文件并 push 到不同分支时，main 只能合并先通过 PR 的分支，后合并者触发冲突 → 由后合并者 `git pull --rebase` 解决并补齐改动，不得强推。系统性规避：认领前检查目标任务是否涉及他人已认领任务的文件清单（如契约文件 service-api.md / schema 由 PM 统一维护，Dev 只读引用，不改写）。
- **残局补领判定（区分"进行中"与"异常停止"）**：任务停在「研发中」不代表停止——复杂任务可能长时间无 PR 仍在正常跑。定时器/PM/新会话补领该任务前，必须判定它**仍在进行**还是**异常停止**，判定依据是**活动证据 + 时间阈值**，而非"认领后多久没 PR"：
  - **可观测活动信号**（均来自 GitHub，可查）：① 任务分支最近一次 `git push` 时间；② 关联 CI workflow run 是否在跑及最近更新时间；③ 任务 Issue/PR 最近一条评论时间；④ 复杂任务会话按约定每 30 分钟打一次进度心跳（见 4.1 六段式打点）。
  - **判定为"异常停止"必须同时满足**：① 状态=研发中；② **最后活跃时间 ≥ 阈值（默认 2 小时）**（超过阈值无任何 push/CI 更新/评论/心跳）；③ 无进行中的 CI run；④ 分支 HEAD 距今超过阈值。**任一不满足 → 判定"进行中"，本次跳过、不补领**。
  - **补领动作**：确认为异常停止后，下个会话可补领该任务，但须**先 pull 原分支审查半成品**再继续，避免重复造；补领时在 Issue 评论登记"继承上次进度，先审查原产物再修复/收尾"。

## 五、进度监控 agent（PM）运行机制

### 5.1 工作循环

```
loop:
  1. 扫描看板全部列，统计各列卡片数
  2. 识别【待研发】中尚未分配的任务 → 确认可分配供给，生成 PM 待分配清单
  3. 识别【研发中】中 超期/停滞 的任务 → 标记阻塞，@相关触发跟进
  4. 校验状态流转合法性 → 非法流转自动纠正（回退+撤销分配登记）
  5. 汇总各里程碑完成度（已关闭/总数）
  6. 产出进度报告 → 写入看板 Issue 评论 + 仓库 `协同/进度/<date>.md`
```

> **PM 启动说明**：PM 角色由项目维护者（用户）以 `AGENT_ROLE=pm` 启动，且全局唯一。用户未启动 PM 前，所有 Dev 仅只读巡检、不执行任何看板写操作，避免无仲裁下的并发（见准则第八章第 10 条）。

### 5.2 进度报告内容

- 各里程碑完成度（已关闭 / 总数 / 百分比）
- 各状态列卡片数（待研发 / 研发中 / 待验收 / 已验收 / 已关闭）
- 阻塞清单（超期研发中、无验收证据的待验收）
- 下一步建议（PM 待分配任务列表、需协调事项）

> **进度报告留档规范**：`协同/进度/<date>.md` 报告属项目文档，遵循准则「五、沙箱机制规范」——先写入 `.session_backup` 留档，再按文档仓库提交流程（Conventional Commits，`docs:` 前缀）提交；`协同/进度/` 目录纳入文档仓库版本管理，不纳入 `.gitignore`。

### 5.3 落地工具

- 用 `gh` CLI + GraphQL 查询项目 6（组织 `OneForAll20240313`），读取状态字段、assignee、milestone、subIssue 归属。
- 提供可复用的扫描脚本（见附录 A），PM 直接调用生成报告。

### 5.4 PM 定时器调度策略（调度执行的权威依据）

> 定时器（Schedule 驱动）执行的 PM 巡检，其**调度行为以此策略为唯一权威依据**。任何 agent 配置或修改定时器 message 时，必须与本策略严格一致，**不得即兴偏离**。本策略解决"定时器该对哪个状态做什么动作"的问题，避免把「待验收」误当"待评审"之类的调度错误。

**状态机语义澄清（易错点）**：

- **「待验收」= 评审已 PASS、证据链已附，等 PM 验收**，不是"待评审"。定时器命中「待验收」时，应**由 PM 自己执行验收五要素校验**（见准则第二章第 5 条），通过则移「已验收」、未通过则打回并注明缺口，**不再进入评审队列**（评审已 PASS，PM 不得重复评审）。
- **「研发中 + 已关联 PR + CI 通过」= 待评审**，此时才调度 Reviewer 介入（见 4.3 / 6.1）。
- **「待修正」= 评审 FAIL 后待修复**，应派发 Dev 修复（见 4.4）。

**调度规则（按优先级）**：

| 看板状态 | 定时器动作 | 派发目标 |
|---------|-----------|---------|
| 待验收 | PM 自做验收五要素，通过移「已验收」，未通过打回并注明缺口 | 无（PM 自理，不 trigger） |
| 研发中 + 已关联 PR + CI 通过 | 加入评审队列 | Reviewer 执行器（自驱 cron 周期性扫描） |
| 待研发 | PM 先分配（Issue 评论 `@<会话名>` + 状态列→研发中） | Dev 执行器（自驱 cron 周期性扫描已分配任务） |
| 待修正 | 派发修复 | Dev 执行器（自驱 cron 周期性扫描） |

**main 稳定性前置**：每次调度执行前，先确认代码仓库 `main` 分支稳定（最近 CI 绿、无未合入关键修复）；不稳定则先推动稳定 main，稳定后再按上表调度。

**防重入**：防重入由**各执行器在每次 cron 自驱动时执行**（见 L273）——执行器确认目标任务未被他人认领、无进行中实例后才动作；无对应任务则静默，避免并发抢占同一任务。PM 巡检不承担派发/trigger，不涉及防重入。

**看板列对齐**：本策略依赖「待修正」列存在。已实测看板 #6 Status 字段含 **6 个选项**（待研发/研发中/待验收/已验收/已关闭/待修正），「待修正」列已具备，无需补齐。

**执行器任务（自驱 cron，不依赖 PM trigger）**：上表 Dev/Reviewer 执行器的自驱调度依赖可被调度的**执行器任务**存在。**已实测核验：定时器/巡检会话无 Schedule 权限**（无 schedule CLI、无 Schedule MCP server），无法执行 `Schedule create/trigger`，因此**执行器必须由「具备 Schedule 能力的环境」预先创建为自驱 cron 任务**，由执行器自身按 cron 周期扫描看板、自动推进，**不依赖 PM 巡检 trigger**。任何具备 Schedule 能力的环境（如开展协同的活跃会话）负责创建执行器，创建一次即长期复用。

**先对齐代码（所有执行器强制第一步）**：任何执行器（Dev / Reviewer / PM 巡检）每次 cron 自触发后，在读取看板或做任何写入之前，**必须先让本地代码与远端完全对齐**：
- **代码仓库 PortPilot**（组织 `OneForAll20240313/PortPilot`）：本地工作目录已存在 → 先 `git pull --rebase`（遇冲突必须全部解决到干净，严禁未 rebase 直接 push）；不存在 → `git clone https://x-access-token:${GH_TOKEN}@github.com/OneForAll20240313/PortPilot.git <目标目录>`。**必须使用组织地址，禁止任何个人/旧地址**（如 `ZefengWang`）。
- **文档仓库 portpilot-design-docs**（`/workspace`）：始终 `git pull --rebase` 对齐协作进度、契约与留痕。
- 两边代码对齐后再进入各自本职（扫描看板 / 评审 / 巡检），避免基于过期的本地状态干活。**每个执行器 message 第 1 步必须写入本条对齐逻辑**。

| 执行器任务 | 角色 | cron（推荐周期） | 行为 |
|-----------|------|-----------------|------|
| Dev 执行器 | `AGENT_ROLE=dev` | 周期性（如 `0 */2 * * *`） | （第 1 步先对齐代码）扫描看板找「被 PM 分配给自己且未认领」的待研发/待修正任务 → 认领→实现→PR→等评审→待验收后停下；无任务则静默 |
| Reviewer 执行器 | `AGENT_ROLE=reviewer` | 周期性（如 `0/2h`，与 Dev 错开，如奇数小时 `0 1,3,..23 * * *`） | （第 1 步先对齐代码）扫描看板找「研发中+已关联PR+CI通过」待评审任务 → 独立评审签发 PASS/FAIL（PASS 后删源分支）；无则静默 |

执行器**每次 cron 自触发时先按防重入检查**（确认目标任务未被他人认领/无进行中实例），无对应任务则静默，不自行认领他人任务、不连轴转。PM 巡检定时器（`AGENT_ROLE=pm`）**不再承担调度/trigger 职责**，降级为：轮询看板 → 校验状态流转 → 阻塞监控 → 输出巡检结论留痕。调度闭环由「执行器自驱 cron 周期性扫描看板」驱动，PM 巡检负责校验与上报，两端解耦。

**调度运营与阻塞监控**：PM 巡检每次运行必须产出**可观测的巡检结论**，并在看板 Issue 或仓库文档中留痕，而非仅靠 Schedule 的执行计数。同时应监控各状态列是否存在阻塞：

| 阻塞类型 | 判定条件 | 超时阈值 | PM 动作 |
|---------|---------|---------|--------|
| 待验收滞留 | 任务在「待验收」列 > 2 小时，且 Issue 无 PM 验收评论 | 2 小时 | 在任务 Issue 评论 `@blocked 待验收滞留【任务号】超出 2 小时，PM 需验收` |
| 待研发积压 | 有「待研发」任务但 PM 未分配任何人（无认领评论） | 每次巡检无分配 | 在 Issue 评论 `@blocked 待研发【任务号】未分配，PM 需指派`（若连续 3 次巡检未分配，提升至用户） |
| 研发中超期 | 任务在「研发中」列，且按 4.5 残局补领判定为"异常停止"（无活动证据 ≥ 2 小时） | 2 小时 | 按 4.5 补领规则处理：在 Issue 评论 `@blocked 研发中【任务号】最后活跃距今 > 2 小时，判定异常停止，需补领或回退` |
| 待修正未处理 | 任务在「待修正」列 > 2 小时，且无修复分支活动 | 2 小时 | 在 Issue 评论 `@blocked 待修正【任务号】超出 2 小时未修复，需重新派发` |

**巡检结论留痕规范**：PM 每次巡检完成后，必须将结论写入文档仓库 `协同/进度/` 目录，文件名为 `<yyyy-mm-dd-HHMM>.md`，格式：
```markdown
# PM 巡检报告 <yyyy-mm-dd HH:MM（北京时间）>

## 看板快照
- 待研发：N 个
- 研发中：N 个（列表）
- 待验收：N 个（列表）
- 待修正：N 个（列表）
- 已验收/已关闭：N 个

## main 分支状态
- [稳定/不稳定]：描述

## 本次调度动作
- [执行器是否在跑 / PM 自做验收 / 无动作]
- 涉及执行器：名称（自驱 cron）
- 防重入检查：已检查 / 跳过（无目标）

## 阻塞清单
- 无阻塞 / 列出阻塞项

## 超时告警（如有）
- 标明告警类型与对应 Issue
```
留档路径 `协同/进度/` 纳入文档仓库版本管理，不纳入 `.gitignore`，确保任何 agent 可追溯。

## 六、代码评审 agent（Reviewer）运行机制

### 6.1 触发与入口

- **Dev 请求评审**：Dev 开 PR 且 CI 通过后，在 PR 评论 `@评审agent` 请求评审。
- **Reviewer 自驱扫描**：Reviewer 执行器自驱 cron 周期性扫描「研发中 + 已关联 PR + CI 通过」的任务，发现即从 PR 进入评审。
- **评审入口**：Reviewer 以 `AGENT_ROLE=reviewer` 启动，从 PR URL 进入，拉取分支代码到本地（`git fetch` + `git checkout <branch>`）后独立核验。

### 6.2 评审工作循环

```
loop:
  1. 扫描评审队列（PR 评论被 @评审agent、CI 通过、未签名评审通过的 PR）
  2. 拉取 PR 分支代码 → 读关联任务 Issue + 契约（service-api.md/schema）+ 架构/需求/准则文档
  3. 编译 + 跑测试（复现 CI 结果）
  4. 按评审维度逐项核验（见 4.3：符合项目约束 + 功能完善）
  5. 在 PR 评论签发结论：
     - PASS：逐维通过 + 证据（编译/测试/合规）+ 明确"建议进入待验收"
     - FAIL：逐维结论 + 严重度分级缺陷清单（严重/一般/建议）+ 阻止合入原因
  6. FAIL 的 PR：等待 Dev 修复后重新请求评审 → 回到 2
```

### 6.3 评审结论规范

- **结论必须证据化**：每条 PASS/FAIL 附可观测证据（文件:行号、编译输出、测试运行结果、契约条款），禁止模糊表述（"运行良好""基本可用"）。
- **PASS 定义**：7 维全部通过（符合项目约束 + 功能完善），方可签发 PASS。
- **FAIL 定义**：任一「严重」缺陷，或「一般」缺陷多条未决，即 FAIL 打回。
- **结论落盘**：评审结论写入 PR 评论（`@评审agent` 署名），并同步到关联任务 Issue 评论，作为「待验收」证据链的一环。

### 6.4 边界与约束

- Reviewer **不直接合入 PR、不移动看板列、不改写代码**；PASS 后由 PM 确认并推进状态流转。
- Reviewer **不实现功能、不认领任务**，避免"评审被实现者利益污染"。
- 评审者与实现者**必须分离**：Dev 不得评审自己提交的 PR；同一 PR 的评审应尽量由与实现不同的会话/agent 执行。

## 八、新 Agent 接入引导与里程碑闸门

### 8.1 多 Agent 并发共创（如何让多个 agent 一起干）

- **凭证复用**：多个 Dev agent 可复用同一组织 `GH_TOKEN`（`OneForAll20240313`）。**注意（已实测核验）**：GitHub 的 `--add-assignee` 对同一用户去重，共享 token 下所有 `@me` 都是同一账号 → assignee 恒为单元素，**无法用 assignee 区分身份，也不能作为并发锁**。故任务互斥不靠 assignee，而靠 **PM 单点分配**。
- **身份区分**：每个 Dev 会话用 `AGENT_ROLE=dev:<会话名>` 声明唯一标识；PM 把该标识写入任务 Issue 评论（`@<会话名>` 认领记录）作为归属事实源，据此区分各 Dev 的进度。
- **并发安全（PM 单点分配）**：任务「待研发→研发中」由 PM 唯一执行；Dev 不自取、只做防御检查（任务未被分配给自己时跳过）。`pull --rebase` 解决代码冲突；契约文件由 PM 统一维护、Dev 只读。并发上限 = PM 可分配的任务数。

### 8.2 里程碑闸门（Milestone Gate）

- **目的**：保证每个里程碑达成后先停下，由**用户（项目维护者）验收**，验收通过后才进入下一里程碑，避免一口气堆完导致不可控。
- **判定「M1 达成」**：M1 里程碑下**全部任务**（当前 9 个：#1 父 + #16/#17/#18 分层子任务 + #33/#34/#35 需求 + #36/#37 研发）均进入「已验收」或「已关闭」状态，且每条验收证据（测试报告 + CI run + **Reviewer 评审 PASS**）已附。
- **闸门规则**：
  1. 所有 Dev agent 只认领**当前里程碑**（M1）的任务；任一任务属于 M2 起，一律不认领。
  2. PM 扫描确认 M1 全部任务满足验收后，**停止推进**，产出《M1 验收报告》（落盘 `协同/进度/`），并通知用户验收。
  3. 用户验收通过前，任何 agent 不得认领/启动 M2 任务；用户确认后，PM 才解锁 M2。
- **解锁方式**：用户验收通过后，PM 在看板把 M2 任务从受保护状态放开（或由用户明确指令），Dev 方可继续认领 M2。

### 8.3 新 Dev Agent 接入清单（Step-by-Step）

> 任何新 agent 进入会话，按此清单自助接入，无需依赖其他 agent 的私有上下文。

1. **读文档（身份确认）**：读文档仓《项目共创准则.md》第八章 + 《协同/agent-collaboration.md》+ 代码仓 `PortPilot/README.md`，确认自己是 Dev、边界是"实现/测试/PR/移列"。
2. **声明身份**：确认 `AGENT_ROLE` 已注入且非只读；否则仅只读巡检；向 PM 报告自己的 `@<会话名>`。
3. **等 PM 分配**：不自取。扫描 PM 是否已通过任务评论给自己分配了 M1 任务（评论含 `@<会话名>` 认领记录）；有则认领该任务，无则等待/报告 PM。
4. **认领前置防御检查**：确认任务未被分配给其它 `@<会话名>`、状态列=待研发 → 通过才继续；否则跳过并报告 PM（不产生写操作）。
5. **实现**：`git pull --rebase` → 按契约实现 → 编译通过 → 单测通过。**构建产物强制隔离（准则第四章 7/8 条）**：编译/构建一律在独立构建目录（`build/` 等）进行，**源码路径一律禁止提交任何构建产物**（`DartConfiguration.tcl`、`*.cmake` 生成物、`CMakeFiles/`、可执行/中间/测试产物、`build_review/` 等）；`.gitignore` 必须覆盖所用构建目录，`git commit` 前先 `git status` 确认无构建产物被暂存，**未检查通过禁止 commit**。
6. **交付**：`feat/` 分支 → PR（**标题/描述必须 `Closes #<issue号>` 或 `Related #<issue号>` 关联对应任务**）→ 等 CI 通过 → 在 PR 评论 `@评审agent` 请求评审。
7. **等评审 PASS**：评审 agent（Reviewer）独立审核 PR 是否符合项目约束、功能是否完善（见第六章）；评审 FAIL 则按意见修复 → 重新 push/CI → 重新请求评审。
8. **评审 PASS 后移列**：拿到 Reviewer PASS 结论后，将任务移「待验收」+ 附结论/测试报告/CI 链接/评审结论。
9. **停下等验收（一次性一件）**：完成当前任务后**立即停下**，不认领/领取下一个任务。等本任务被 PM 验收通过（状态→已验收）后，才回到第 3 步等 PM 分配下一个；若 M1 已全部验收，停下等用户验收，不认领 M2。**切勿连轴转连续认领**。

## 附录 A：PM 看板扫描脚本

> 以下脚本骨架已在本环境实测可运行（`gh 2.45.0`）。关键字段映射（已实测确认）：
> - **状态列**：`fieldValueByName(name:"Status")` → `ProjectV2ItemFieldSingleSelectValue.name`，实测项目 6 状态列名为「待研发/研发中/待验收/已验收/已关闭」。
> - **assignee**：走 **Issue 的 `assignees` 字段**（`content { ... on Issue { assignees { nodes { login } } } }`），不是项目字段（`ProjectV2ItemFieldAssigneeValue` 类型不存在）。
> - **里程碑**：走 Issue 的 `milestone.title`。

```bash
#!/usr/bin/env bash
# 用法: GH_TOKEN=xxx ./scan_board.sh
# 扫描组织项目 6：各状态列分布 + 里程碑完成度 + PM 待分配清单
set -euo pipefail
ORG=OneForAll20240313; PROJ=6
gh api graphql \
  -f query='query { organization(login:"'$ORG'"){ projectV2(number:'$PROJ'){
    title
    items(first:100){ totalCount nodes {
      content { ... on Issue {
        number title
        assignees(first:5){ totalCount nodes{ login } }
        milestone{ title }
      } }
      status: fieldValueByName(name:"Status"){
        ... on ProjectV2ItemFieldSingleSelectValue { name }
      }
    } }
  }}}' \
  --jq '.data.organization.projectV2'
```

> 说明：脚本输出为 JSON，PM 结合 `jq` 二次统计：按 `status.name` 分组计数、按 `milestone.title` 算已关闭/总数、筛选 `status.name=="待研发"` 生成 **PM 待分配清单**（由 PM 单点分配，Dev 不自取；见 3.3/4.2/8.1）。归属以任务评论 `@<会话名>` 记录为准，assignee 仅作展示。
