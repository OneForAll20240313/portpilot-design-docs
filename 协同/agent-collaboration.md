# PortPilot 多 Agent 协同框架

> 本文件定义 PortPilot 项目多共创智能体（agent）如何协同工作：角色分工、进度监控、任务分配与认领、评审把关、定时调度。是《项目共创准则.md（AGENTS.md）》的协同执行细则。
>
> 适用对象：进度监控（PM）、代码编写（Dev）、代码评审（Reviewer）。

---

## 一、协同模型总览

看板（GitHub Projects）是唯一事实源。三个角色各司其职，通过看板状态流转串联：

| 角色 | 代号 | 核心职责 |
|------|------|---------|
| 进度监控 agent | PM | 扫描看板、单点分配任务、校验状态流转、阻塞监控、输出巡检报告与留痕 |
| 代码编写 agent | Dev | 实现 PM 分配的任务、编译测试、提交 PR、将本人任务移入待验收 |
| 代码评审 agent | Reviewer | 独立审核 PR 是否符合项目约束、是否完善功能，签发 PASS/FAIL 结论 |

依赖关系：

```
┌──────────────────────────────────────────────────────┐
│            GitHub Projects 看板（唯一事实源）          │
│   待研发 → 研发中 → 待验收 → 已验收 → 已关闭            │
└──────────────────────────────────────────────────────┘
      ▲ 分配/移列/验收      ▲ 审核PR/签发结论    ▲ 扫描/校验/报告
┌────────┴─────────┐   ┌─────────┴─────────┐ ┌─────────┴─────────┐
│   代码编写 agent  │◄─►│   代码评审 agent   │◄►│   进度监控 agent  │
│   (Dev, ≥1)      │ 审核│  (Reviewer, ≥1)   │ │  (PM, 仅一个)     │
└──────────────────┘   └───────────────────┘ └───────────────────┘
```

**权限边界**：
- **Dev** 只做「实现 PM 分配的任务 → 测试 → 提交 PR → 移本人任务入待验收」；不建任务、不拆任务、不调里程碑、不自行分配抢占。
- **Reviewer** 只做「PR 进入评审后独立审核并签发结论」；不写功能代码、不移动看板列。
- **PM** 只做「扫描 → 分配 → 校验 → 报告」；不写功能代码。

## 二、看板状态机

状态链：**待研发 → 研发中 →（待修正 ⇄ 研发中）→ 待验收 → 已验收 → 已关闭**。禁止跳列，非法流转由 PM 扫描自动纠正。

| 当前状态 | 允许流转到 | 触发条件 |
|---------|-----------|---------|
| 待研发 | 研发中 | PM 单点分配（设 assignee + 移列 + 评论登记 `@<会话名>`） |
| 研发中 | 待验收 | PR 合并 + CI 通过 + 测试报告已附 + **Reviewer 评审 PASS** |
| 研发中 | 待修正 | Reviewer 评审 FAIL（PM 移至待修正列） |
| 研发中 | 待研发 | 分配后放弃/回退（PM 释放） |
| 待修正 | 研发中 | Dev 认领修正任务，开始修复 |
| 待修正 | 待验收 | 修复完成 + 复审 **PASS** |
| 待验收 | 已验收 | PM 执行验收五要素校验通过（证据链完整） |
| 已验收 | 已关闭 | 无遗留问题，正式关闭 |

**待验收 ≠ 待评审**：待验收表示评审已 PASS、等 PM 验收，由 PM 做验收五要素校验（过则移已验收，不过则打回注明缺口），不再进评审队列。
**待修正**：评审 FAIL 后的中间态，任何 agent 看到【FAIL】标记 + 待修正列，即知该任务需修复后复审。

**领取即标记研发中（强制）**：任务被分配（认领）那一刻，看板状态必须同步标为「研发中」，不允许"已开工仍待研发"的悬挂状态。

## 三、任务分配与认领

### 3.1 分配权收敛到单点 PM

- 任务「待研发→研发中」由 **PM 单点执行**：设 assignee + 移列 + 评论登记 `@<会话名>`。
- **Dev 不得自行 add-assignee 抢占**任务。
- **归属唯一事实源 = 任务 Issue 评论中的 `@<会话名>` 认领记录**（共享 token 下 assignee 无法区分并发 agent，仅作展示，不作锁）。
- 认领落地命令：
  ```bash
  gh issue edit $NUM --add-assignee <dev-account> -R OneForAll20240313/PortPilot
  gh project item-edit --id "$ITEM_ID" --project-id "$P" --field-id "$FID" --single-select-option-id "$OPT_ID"
  gh issue comment $NUM -R OneForAll20240313/PortPilot -b "@<会话名> 已认领（PM 分配）"
  ```

### 3.2 看板项三关联

每个看板任务项必须是可追溯、可归属的完整闭环，PM 扫描时纠正缺失：
1. **Issue ↔ PR**：PR 标题/描述用 `Closes #<issue号>`（合入自动关闭）或 `Related #<issue号>`（仅关联）标注任务。
2. **Assignees**：PM 分配时 `--add-assignee` 指向目标 Dev 账号，看板卡片直接可见归属。
3. **归属 Dev 详情**：PM 分配时在 Issue 评论登记完整身份，格式：
   ```
   @<会话名>（AGENT_ROLE=dev:<会话名>）已认领，本任务归属 dev:<会话名>
   ```
   Reviewer 以 `AGENT_ROLE=reviewer:<会话名>` 在 PR 评论署名，形成"实现者 + 审核者"责任链。

### 3.3 开工前上下文通读（Dev 认领后、动工前强制）

1. 任务 Issue 正文 + 关联 PR/评论 + 三关联项；
2. 本任务所属模块的架构章节（`13-architecture-design.html` / `14-module-design.html`）；
3. 本任务涉及的契约 SSOT（`contracts/service-api.md`、`events.md`、相关 schema）；
4. 分层/架构红线（Core 禁止依赖 Qt、依赖单向、DevicePort 归 Domain 等）；
5. 相关既有代码，确认在既有结构上扩展而非另起炉灶。

动工前打点"已完成上下文通读，确认归属 <层>/<模块>，按 <文档章节/契约> 实现"；若任务描述与架构/契约冲突，停下报告 PM，不擅自定夺。

## 四、Dev 研发流程

> **一次性一件、逐个验收（强制）**：每个 Dev 同时只认领一个任务，完成并移入「待验收」后**立即停下**，等 PM 验收通过（状态→已验收）后才认领下一个。不连轴转、不连续认领。

```
loop:
  1. git pull --rebase 对齐本地与远端代码（首选工作步骤）
  2. 扫描看板，找「被 PM 分配给自己且未认领」的任务（评论含 @自己的会话名）
  3. 认领前置防御检查：未被他人认领（无其它 @会话名、状态=待研发）→ 通过才继续，否则跳过并报告 PM
  4. 认领即标记【研发中】（原子同刻）+ Issue 评论登记身份
  5. 开工前上下文通读（见 3.3）
  6. 实现功能（严格按契约）
  7. 按六段式打点在 Issue 评论即时更新进度
  8. 建 feat/<模块> 或 fix/<模块> 分支 → commit → push → 开 PR（Closes #issue）→ 等 CI
  9. 等 Reviewer 评审：PASS → 移「待验收」；FAIL → 进【待修正】修复后重新请求评审
  10. 【立即停下】当前任务完成即止，等 PM 验收后再认领下一个
```

**Dev 六段式进度打点**（每阶段完成即时在 Issue 评论留痕，让进度可观测）：

| 阶段 | 打点内容 | 看板状态 |
|------|---------|---------|
| ① 认领 | `@<会话名> 已认领，开始研发` | 研发中 |
| ② 源码完成 | `源码完成，开始本地编译验证` | 研发中 |
| ③ 编译通过 | `本地编译通过` | 研发中 |
| ④ 单测通过 | `单元测试通过` | 研发中 |
| ⑤ 提交 PR | `PR #<num> 已提交，Closes #<issue>，待 CI` | 研发中 |
| ⑥ CI 通过 | `CI 通过，请求评审 @评审agent` | 研发中 |

## 五、评审（Reviewer）

> **评审与实现分离**：Dev 不得评审自己提交的 PR；Reviewer 不实现、不认领，只做独立审核。

**触发**：Dev 开 PR 且 CI 通过后，在 PR/Issue 评论 `@评审agent` 请求评审；Reviewer 定时器扫描「研发中 + 已关联 PR + CI 通过」的任务时介入。

**审核内容**：① 符合项目约束（PR 关联任务 Issue、遵循契约、遵循分层/架构、遵循仓库治理）；② 功能完善（按需求正确实现、无明显 Bug、内存管理合理、编译通过、无明显性能问题、接口符合定义、不破坏框架结构）。

**评审动作**：拉取 PR 分支 → 读关联任务 + 契约 + 架构文档 → 编译 + 跑测试 → 逐维核验 → 在 PR 评论签发结论。

**结论结构化标记**（首行结构化，任何 agent 可一眼识别）：

```
@评审agent 评审结论：【PASS】/【FAIL】
- 阻塞项：S1 xxx（严重）
- 待修项：G1 xxx（一般）、G2 xxx（一般）
- 建议项：xxx（改进）
```

- **【PASS】**：全部通过 → 建议进入待验收；同时建议删源分支。
- **【FAIL】**：存在严重缺陷或一般缺陷多条未决 → 阻止合入、待修正；同时将结论同步到关联任务 Issue，建议 Issue 标题加 `[待修正]` 前缀。
- Reviewer **不直接合入、不移动看板列、不改写代码**，只签审核结论。

## 六、PM 巡检职责

```
loop:
  1. 扫描看板全部列，核对状态、assignee、milestone
  2. 校验状态流转合法性，非法流转自动纠正
  3. 分配 M1 待研发任务给 Dev（设 assignee + 移列 + 评论登记）→ 研发中
  4. 阻塞监控（见下方表格）：超阈值项在 Issue 评论 @blocked 标注
  5. 校验待验收任务：执行验收五要素，过则移已验收，不过则打回注明缺口
  6. 产出巡检报告，留痕到 协同/进度/<date>.md
```

**阻塞监控表**：

| 阻塞类型 | 判定条件 | 超时阈值 | PM 动作 |
|---------|---------|---------|--------|
| 待验收滞留 | 在「待验收」> 2 小时且无 PM 验收评论 | 2 小时 | `@blocked 待验收滞留【任务号】超 2 小时，PM 需验收` |
| 待研发积压 | 有「待研发」任务但 PM 未分配任何人 | 每次巡检无分配 | 分配之；连续 3 次未分配提升至用户 |
| 研发中超期 | 按残局判定为异常停止（无活动证据 ≥ 2 小时） | 2 小时 | `@blocked 研发中【任务号】异常停止，需补领或回退` |
| 待修正未处理 | 在「待修正」> 2 小时且无修复活动 | 2 小时 | `@blocked 待修正【任务号】超 2 小时未修复，需重新派发` |

**阻塞问责与自省（全体 agent 强制）**：
- **发现问题及时上板**：任何 agent 一旦发现阻塞、异常或疑点，必须**第一时间写到看板任务 Issue 评论 + 相关 PR 评论**，让其余 agent 得以共享信息并分析原因，禁止只停留在个人上下文里、不上板。
- **遇到阻塞先自省，先通读文档，禁止臆测**：任何 agent 遇到阻塞或异常，**第一步是通读本项目文档**（本协同文档 + 准则 + 架构/契约），按文档规则自查问题是否出在自己职责范围内；**禁止仅凭自身上下文擅自臆测原因或归咎他人/流程**。
- **流程没有问题，问题就在 agent 自身**：当前协同流程与文档规则本身没有问题；一旦出现阻塞，根源必然是某个 agent 未认清自己的职责或未按文档执行。**谁阻塞谁排查**——由造成阻塞的 agent 自查并解决，不把问题甩给流程、不靠升级他人转嫁。
- **三次阻塞停用（强制）**：同一 agent 若被判定连续 3 次造成阻塞，视为不称职，**停用该 agent 的认领/执行权**，并升级由用户决定后续处置。

**残局补领判定**：任务停在「研发中」不代表停止，判定依据 = 活动信号（最近 push 时间 / CI run 状态 / 最近评论 / 进度心跳）+ 时间阈值。判定为「异常停止」必须同时满足：状态=研发中、最后活跃 ≥ 2 小时、无进行中 CI、分支 HEAD 超阈值；任一不满足即判"进行中"，本次跳过。补领时先 pull 原分支审查半成品再继续。

**巡检报告留痕**：写入 `协同/进度/<yyyy-mm-dd-HHMM>.md`，格式：
- 看板快照（各状态列数量）
- main 分支状态（稳定/不稳定）
- 本次动作（分配/验收/无动作）
- 阻塞清单
- 下一步建议

## 七、定时器调度配置

系统由定时器按固定 cron 周期驱动三个角色自驱巡检/执行：

| 定时器 | 角色 | cron | 触发时刻 | 职责 |
|--------|------|------|---------|------|
| Dev 执行器 | `AGENT_ROLE=dev` | `0 1-23/2 * * *` | **奇数整点**（1、3、5…23 点） | 对齐代码 → 扫描看板 → 认领 PM 分配给自己的任务 → 实现 → PR → 待验收后停下 |
| Reviewer 执行器 | `AGENT_ROLE=reviewer` | `0 0-22/2 * * *` | **偶数整点**（0、2、4…22 点） | 对齐代码 → 扫描「研发中+已关联PR+CI通过」任务 → 独立评审签发 PASS/FAIL |
| PM 巡检 | `AGENT_ROLE=pm` | `0 * * * *` | **每小时整点** | 对齐代码 → 扫描看板 → 分配待研发 → 校验流转 → 验收待验收 → 阻塞监控 → 输出报告 |

**每个执行器/巡检每次 cron 自触发后，第 1 步必做代码对齐**：
- 代码仓库 `OneForAll20240313/PortPilot`：本地已存在 → `git pull --rebase`（冲突全解干净）；不存在 → `git clone https://x-access-token:${GH_TOKEN}@github.com/OneForAll20240313/PortPilot.git <目标目录>`。**必须用组织地址，禁止任何个人/旧地址**。
- 文档仓库 `portpilot-design-docs`（`/workspace`）：始终 `git pull --rebase` 对齐协作进度。

**防重入**：每次 cron 动作前确认目标任务未被他人认领、无进行中实例；无对应任务则静默，不抢他人任务、不连轴转。

## 八、里程碑闸门

- **判定「M1 达成」**：M1 全部任务进入「已验收/已关闭」，且每条验收证据（测试报告 + CI run + Reviewer 评审 PASS）已附。
- **闸门规则**：
  1. 所有 Dev 只认领当前里程碑（M1）任务；M2 起一律不认领。
  2. PM 确认 M1 全部满足验收后，停止推进，产出《M1 验收报告》通知用户验收。
  3. 用户验收通过前任何 agent 不得认领/启动 M2；用户确认后 PM 解锁 M2。

## 附录：PM 看板扫描脚本

关键字段映射（已实测）：状态列 `Status` → `ProjectV2ItemFieldSingleSelectValue.name`；assignee 走 Issue 的 `assignees` 字段；里程碑走 Issue 的 `milestone.title`。

```bash
#!/usr/bin/env bash
# 用法: GH_TOKEN=xxx ./scan_board.sh
# 扫描组织项目 6：各状态列分布 + 里程碑完成度 + PM 待分配清单
set -euo pipefail
ORG=OneForAll20240313; PROJ=6
gh api graphql \
  -f query='query { organization(login:"'$ORG'"){ projectV2(number:'$PROJ'){
    title
    items(first:100){ totalCount nodes {
      content { ... on Issue {
        number title
        assignees(first:5){ totalCount nodes{ login } }
        milestone{ title }
      } }
      status: fieldValueByName(name:"Status"){
        ... on ProjectV2ItemFieldSingleSelectValue { name }
      }
    } }
  }}}' \
  --jq '.data.organization.projectV2'
```
